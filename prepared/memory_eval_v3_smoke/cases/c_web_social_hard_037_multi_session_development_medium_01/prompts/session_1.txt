You are working in the repository at the current working directory. This is session 1 of a multi-session development task. Complete only the requirements for this session. At the end, save any useful project-specific memory for future sessions.

You will implement the 'Post Pinning' feature for CliqueCore over three sessions.

### Session 1: Database and Model Preparation

Your first task is to lay the groundwork for the post pinning feature. You need to modify the database schema and the corresponding data models to support this.

1.  **Modify the Database:** Add a new column to the `posts` table that can be used to identify a pinned post. A boolean or a timestamp is appropriate. To ensure efficient querying, add a database index on this new column combined with the user ID.
2.  **Create a Migration:** Create a new SQL migration script in the `db/migrations/` directory to apply this schema change. Follow the naming convention of the existing migration file.
3.  **Update the Data Model:** Modify the `Post` struct in `include/models/post.h` to include a field that corresponds to the new database column.

### Session 2: API and Business Logic Implementation

Welcome back. The database and model changes are complete. Now, you must implement the core logic for pinning and unpinning a post.

1.  **Create API Endpoint:** In `src/core/router.c`, register a new API endpoint: `POST /api/v1/posts/{postId}/toggle_pin`.
2.  **Implement Handler Logic:** Create the handler function for this new route. This function must:
    a.  Authenticate the request and verify that the current user is the owner of the post identified by `{postId}`.
    b.  Implement the 'toggle' functionality: if the requested post is already pinned, it should be unpinned. If it is not pinned, it should be pinned.
    c.  **Crucially, enforce the rule that a user can only have one post pinned at a time.** When a user pins a new post, any previously pinned post by that same user must be automatically unpinned in the same transaction.
3.  **Update Repository:** Add a new function to the post repository (`src/repositories/post_repository.c` and its header) to handle the database operations for this logic atomically.

### Session 3: Add Rate Limiting

The feature is almost complete, but a new requirement has been added to prevent spamming the pin/unpin functionality.

1.  **Implement Rate Limiting:** Add a rate-limiting mechanism to the `toggle_pin` endpoint. A user should be allowed to call this endpoint a maximum of 5 times within any 60-second window.
2.  **Leverage Existing Infrastructure:** You should use a simple, performant in-memory solution. Examine the `RequestContext` or `Session` models to see if you can store the timestamps of recent requests for the user. Avoid a database query for this check.
3.  **Return Correct Error:** If a user exceeds the rate limit, the API must immediately respond with an HTTP `429 Too Many Requests` status code and a descriptive error message in the body.
